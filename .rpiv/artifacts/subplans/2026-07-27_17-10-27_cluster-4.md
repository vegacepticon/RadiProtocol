# Sub-Plan: Default a Start node into newly created protocols

## Synthesis Notes

- **Single-slice fan-in.** Only one design (Slice 4) was supplied for this cluster, so there is no intra-cluster overlap to merge. The synthesis work is binding the design's decisions to the research's cross-slice constraints and exporting the seam the root merge wires against the store caller and the other slices of the seven-change feature.
- **No file overlap with any sibling slice (research-confirmed).** Slice 4 edits only `src/protocol/protocol-document.ts` and `src/__tests__/protocol-document-store.test.ts`. The research's edit inventory for the other slices shows: Slice 1 → `inline-runner-modal.ts` + `inline-runner.css` + i18n; Slice 2 → `snippet-service.ts`/`snippet-model.ts`/`insert-snippet-modal.ts`/`snippet-tree-picker.ts`/`inline-runner-modal.ts`/README; Slice 3 → `protocol-editor-view.ts` (`EDITABLE_NODE_KINDS`) + `node-picker-modal.ts`; Slice 5 → `snippet-tree-picker.css`. None of these touch `protocol-document.ts` or `protocol-document-store.test.ts`. No cross-slice edit-region collision; the root merge needs no file-level reconciliation for this cluster.
- **Conceptual-only reference to Slice 3's file.** The design inlines the Start color and node dimensions as literals and cross-references `NODE_KIND_DEFAULTS.start` (`protocol-editor-view.ts:248`) and `DEFAULT_NODE_WIDTH/HEIGHT` (`:17-18`) by *comment only* — no import, no edit. Slice 3 edits `EDITABLE_NODE_KINDS` at `protocol-editor-view.ts:256`, a different line. The two slices therefore compose without conflict even though both name `protocol-editor-view.ts`; the only coupling is the drift hazard flagged as r1 (if Slice 3 or any future slice changes the Start color/default dimensions, this seed must be updated to match).
- **Store-caller seam (research Integration Point).** `ProtocolDocumentStore.create()` (`src/protocol/protocol-document-store.ts:95`) calls `createEmptyProtocolDocument(id, safeTitle, now)` and persists the result via `write()`. The new `startNodeId` parameter is optional with a generated default, so the store's signature and call site are unchanged — the store simply persists a document that now carries one Start node. `src/main.ts:207-215` (`createAndOpenProtocol`) is likewise untouched: it calls `create(...)` then `activateProtocolEditorView(file.path)`, and the editor loads the seeded document via `loadProtocol`. This is the seam exported for the root merge: any cluster that later wraps or replaces the creation flow must preserve the "newly created protocol carries one Start node" invariant, or re-introduce the `noStartNode` validation failure this slice eliminates.
- **Validator seam (research-confirmed, no change).** `GraphValidator.validate()` (`src/graph/graph-validator.ts:60-62`) early-returns `noStartNode` when there are zero start nodes; a single-Start-node graph with no edges is already valid (the reachability check skips the start node and there are no other nodes to be unreachable). The research explicitly confirms "A single-start-node graph with no edges is valid (zero validator errors)." No `GraphValidator` change is needed or in scope — the seed works against the existing validator as-is. Slice 4 does not depend on any validator change from another cluster.
- **ID generation — hybrid preserves purity.** The design's chosen fork (optional `startNodeId` parameter defaulting to `node-${now.getTime()}-${Math.random().toString(36).slice(2, 8)}`) uses the already-injected `now` clock for the timestamp rather than a fresh `Date.now()`, keeping the function deterministic under the injected clock and avoiding an uncontrollable side effect in a pure function. The default-parameter expression legally references the earlier `now` parameter. Tests and a future import flow can pass an explicit id. This is the cleaner of the two slice-map options and is preserved as-is.
- **Viewport visibility — out of scope, confirmed by research.** The seeded node sits at world `(0,0)`, which the editor maps to surface center via `PROTOCOL_EDITOR_ORIGIN_X/Y` (`protocol-editor-view.ts:21-22`), and `restoreViewportState` scrolls there by default when `doc.viewport` is undefined. No pan-to-node or auto-centering logic is introduced — explicitly out of scope per the slice map and confirmed unnecessary by the research. No coupling to any cluster that might touch viewport handling.
- **Test scope (research-confirmed).** Only `src/__tests__/protocol-document-store.test.ts` `create` tests gain new assertions (`result.doc.nodes.length === 1`, `result.doc.nodes[0].kind === 'start'`). The research confirms no dedicated `createEmptyProtocolDocument` test file exists and that other test fixtures construct `ProtocolDocumentV1` directly with `nodes: []` rather than via the factory, so they are unaffected. The r2 risk asks validate to confirm by grep that no hidden reference asserts empty nodes.

## Risk Flags
- **r1** — The Start node color (`rgba(76, 175, 80, 0.28)`) and dimensions (`width:200, height:80`) are inlined as literals in the pure protocol layer with comments cross-referencing `NODE_KIND_DEFAULTS.start` (`src/views/protocol-editor-view.ts:248`) and `DEFAULT_NODE_WIDTH/DEFAULT_NODE_HEIGHT` (`:17-18`), rather than imported, to preserve the `views/ → protocol/` architecture boundary (lower layers never import from `views/`). If those view-layer constants change, the seeded node silently drifts from the user-created-node shape with no compile-time signal. Reviewer should rule: is inlining-with-comment acceptable (the design's choice, matching the existing boundary), or should the values be promoted to a shared constant both layers may import? Rule pass if the boundary rationale holds and a code-comment cross-reference is deemed sufficient; flag for a follow-up if the grade panel wants the values shared.
- **r2** — The change flips `createEmptyProtocolDocument`'s `nodes` from `[]` to a 1-element array. The research states no dedicated test file exists and other fixtures build `ProtocolDocumentV1` directly, so nothing should assert empty nodes — but a hidden assertion of `nodes.length === 0` or `nodes` deep-equal `[]` would break. Reviewer should grep every `createEmptyProtocolDocument` reference across `src/` and `src/__tests__/` and confirm none asserts empty nodes. Rule pass if no such assertion exists; fail if one is found (the test would need updating in the same phase).

## Phase 1: Default a Start node into newly created protocols
### Changes
- `src/protocol/protocol-document.ts` — add an optional 4th parameter `startNodeId` to `createEmptyProtocolDocument()` with default `` `node-${now.getTime()}-${Math.random().toString(36).slice(2, 8)}` `` (referencing the already-injected `now` clock, not a fresh `Date.now()`); populate the returned document's `nodes` array with one Start `ProtocolNodeRecord`: `{ id: startNodeId, kind: 'start', x: 0, y: 0, width: 200, height: 80, color: 'rgba(76, 175, 80, 0.28)', fields: {} }`; inline the color and dimensions as literals with inline comments cross-referencing `NODE_KIND_DEFAULTS.start` (`src/views/protocol-editor-view.ts:248`) and `DEFAULT_NODE_WIDTH`/`DEFAULT_NODE_HEIGHT` (`src/views/protocol-editor-view.ts:17-18`) so the seed stays in sync with the editor's user-created-node shape without importing view-layer constants; update the JSDoc to state the function now seeds a default Start node (so the "empty" misnomer is explained at the call site) and to document the new optional `startNodeId` parameter (pass an explicit id for deterministic tests/imports). Keep the function name `createEmptyProtocolDocument` (no cascade rename); keep `edges: []` and `schema`/`version`/`id`/`title`/`createdAt`/`updatedAt`/`layoutDirection` unchanged.
- `src/__tests__/protocol-document-store.test.ts` — extend the two `ProtocolDocumentStore — create` tests (using the existing `makeVault()` mock-factory pattern) to assert `result.doc.nodes.length === 1` and `result.doc.nodes[0].kind === 'start'`. Do not assert the generated `id` format in the store tests (it is random by default); deterministic-id assertions belong to a direct `createEmptyProtocolDocument` call with an explicit `startNodeId`, added if a dedicated factory test is introduced (optional, not required by the design).

- [ ] `edges` of the returned document is `[]` and `schema`/`version`/`id`/`title`/`createdAt`/`updatedAt`/`layoutDirection` are unchanged from prior behavior.

#### Manual Verification:

- [ ] The seeded Start node can be selected, dragged, edited, connected, and deleted like any user-created Start node (it is plain `ProtocolNodeRecord` data, not special-cased anywhere).
