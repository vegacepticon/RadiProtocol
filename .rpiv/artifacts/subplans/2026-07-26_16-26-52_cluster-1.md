# Sub-plan: snippet-create-from-selection

## Synthesis Notes
- **Cross-slice contract (published → consumed).** Slice 1 decides and publishes
  `SnippetEditorOptions.initialTemplate?: string` (optional, empty-when-absent,
  threaded through `emptyMdTemplateDraft()`'s new 4th param `initialTemplate:
  string = ''`). Slice 2 consumes it as fixed —
  `handleCreateSnippetFromSelection()` constructs
  `new SnippetEditorModal(this.app, this.plugin, { mode: 'create', initialFolder,
  initialTemplate: template })` exactly as Slice 1's `handleCreateSnippet()`
  does. No redesign of the contract in Slice 2; the seam is wired verbatim.
- **i18n overlap, no collision.** Both slices edit `src/i18n/locales/en.json` and
  `src/i18n/locales/ru.json`, but in disjoint namespaces: Slice 1 adds
  `snippetEditor.createdNotice` (consumed only by `handleCreateSnippet()` in
  `main.ts`); Slice 2 adds `protocolRunner.createSnippetFromSelection`
  (consumed only for the runner footer button's aria-label). Both are additive
  to their respective namespaces and neither reads the other's key — merged
  into two phases with no conflict. (Note: Slice 2 deliberately does NOT reuse
  `snippetEditor.createdNotice` for a runner-button save toast, to avoid
  coupling to an unpublished detail of Slice 1; the runner path emits no
  save-confirmation Notice by design.)
- **Disjoint source files.** Slice 1 edits `src/views/snippet-editor-modal.ts`
  and `src/main.ts`; Slice 2 edits `src/views/inline-runner-modal.ts` and
  `src/styles/inline-runner.css`. No file is touched by both slices, so the
  phases apply independently and order matters only for the contract
  dependency.
- **Phase ordering.** Slice 1 (`depends_on: []`) → Phase 1; Slice 2
  (`depends_on: [1]`) → Phase 2. The dependency is the `initialTemplate`
  contract: Slice 2's `inline-runner-modal.ts` imports and constructs
  `SnippetEditorModal` with `initialTemplate`, which only compiles once Slice
  1's interface extension lands. Phase 2 must not be implemented before Phase 1.
- **No merges.** The two slices are tightly cohesive within themselves and
  disjoint across each other; no phases are merged. Each slice becomes exactly
  one phase, preserving every decision in its source design verbatim.
- **Backward compatibility preserved by construction.** `initialTemplate` is
  optional and `emptyMdTemplateDraft`'s 4th param defaults to `''`, so the
  existing create-mode caller `SnippetManagerView.openCreateModal()`
  (`snippet-manager-view.ts:258-267`) compiles and runs unchanged — confirmed by
  both designs and the research. No call-site edit required in either phase.

## Risk Flags
- **r1** — `SnippetEditorModal` is opened from `InlineRunnerModal`, which is a
  plain floating div (custom DOM overlay), not an Obsidian `Modal` subclass.
  The research's #1 recurring failure pattern is "picker/modal opened from a
  custom backdrop stacks behind it" (commits `c0bb3ee`, `164b8e6` consumed two
  plan cycles on this). Slice 2's design argues `SnippetEditorModal` is a real
  Obsidian `Modal` that mounts to `document.body`, so it should stack above the
  inline runner overlay by Obsidian's default modal z-index — but this is an
  unverified assumption, not a tested behavior. **Validate** by opening the
  runner, selecting text, clicking the create-snippet button, and confirming
  the modal renders above the runner (the runner remains visible behind it).
  If it stacks behind, the fix is a z-index rule on the modal's `modalEl`
  scoped class — out of scope for this sub-plan unless validation fails.

## Phase 1: Pre-fill snippet editor from selection + standalone create-snippet command
### Changes
- `src/views/snippet-editor-modal.ts` — add `initialTemplate?: string` to the
  `SnippetEditorOptions` interface (additive optional field, after the existing
  `disableFolderPicker?`); add a 4th parameter `initialTemplate: string = ''`
  to `emptyMdTemplateDraft()` and use it for the `template` field instead of the
  literal `''`; in the constructor create-mode branch pass
  `options.initialTemplate ?? ''` as the 4th arg to `emptyMdTemplateDraft()`.
  The edit-mode branch, `mountChipEditor` call, and `handleSave()`'s
  `draftToSave` spread are untouched — the pre-filled `template` flows through
  the chip editor (`templateArea.value = draft.template` at
  `snippet-chip-editor.ts:125`) and into `SnippetService.save()` unchanged.
- `src/main.ts` — import `SnippetEditorModal`; register a new
  `create-snippet` `addCommand` block (after the `insert-snippet` command at
  `main.ts:96-100`) with `name: 'Create snippet from selection'`; add a
  `handleCreateSnippet()` method mirroring `handleInsertSnippet()`
  (`main.ts:285-297`) but reading `activeView?.editor?.getSelection() ?? ''` as
  `initialTemplate` (NOT `editor.replaceSelection`), with no md-guard bail
  (opens with an empty template when there is no active MarkdownView or no
  selection, so the command remains useful for authoring from scratch); after
  `await modal.result`, show `new Notice(this.i18n.t('snippetEditor.createdNotice'))`
  when `result.saved`.
- `src/i18n/locales/en.json` — add `"createdNotice": "Snippet created."` to the
  `snippetEditor` namespace.
- `src/i18n/locales/ru.json` — add `"createdNotice": "Сниппет создан."` to the
  `snippetEditor` namespace.

  regressions in existing snippet-editor / chip-editor suites.
#### Manual Verification:

  initialFolder, initialTemplate: 'selected text' })` and opening it mounts the

- [ ] Constructing the modal without `initialTemplate` (the existing

## Phase 2: Create snippet from selection in Runner footer
### Changes
- `src/views/inline-runner-modal.ts` — import `SnippetEditorModal`; add two
  class fields `createSnippetBtnEl: HTMLButtonElement | null = null` and
  `boundSelectionHandler: (() => void) | null = null` next to the existing
  `boundKeyHandler` field; in the `render()` footer-teardown block
  (`inline-runner-modal.ts:426-434`) wrap the close + new create-snippet buttons
  in a `rp-runner-footer-left` group, create the create-snippet button
  (`cls: 'rp-inline-runner-create-snippet-btn rp-runner-icon-btn'`, icon
  `file-plus`, `disabled = true` initially), store it in `createSnippetBtnEl`,
  and call `updateCreateSnippetButtonState()`; in `open()` (after the
  `boundKeyHandler` attach at `:226-227`) attach `mouseup` on `contentEl` and
  `selectionchange` on `document` to `boundSelectionHandler`; in `close()`
  (mirroring the `boundKeyHandler` detach at `:251-254`) detach both listeners
  and null `createSnippetBtnEl` + `boundSelectionHandler`; add three private
  methods — `getSelectedContentText()` (returns `window.getSelection()`
  toString iff the selection's anchor node is contained in `contentEl`, else
  `''`), `updateCreateSnippetButtonState()` (sets `createSnippetBtnEl.disabled`
  based on whether `getSelectedContentText()` is non-empty), and
  `handleCreateSnippetFromSelection()` (captures the selection text before
  opening, constructs `new SnippetEditorModal(this.app, this.plugin, { mode:
  'create', initialFolder: this.plugin.settings.snippetFolderPath,
  initialTemplate: template })`, `open()`s it, `await modal.result`).
- `src/styles/inline-runner.css` — add `.rp-runner-footer-left` (display flex,
  align-items center, gap `--size-4-2`, justify-content flex-start) holding
  close + create-snippet on the left of the `space-between` footer row; add
  `.rp-runner-icon-btn:disabled, .rp-runner-icon-btn:disabled:hover` (opacity
  0.4, cursor not-allowed, background transparent, color `--text-muted`) so the
  disabled create-snippet button reads as inactive (additive — also styles the
  Back/Redo/Skip buttons' disabled state, currently set via `.disabled = true`
  but previously unstyled).
- `src/i18n/locales/en.json` — add `"createSnippetFromSelection": "Create
  snippet from selection"` to the `protocolRunner` namespace (used only for
  the create-snippet button's aria-label).
- `src/i18n/locales/ru.json` — add `"createSnippetFromSelection": "Создать
  сниппет из выделения"` to the `protocolRunner` namespace.

### Success Criteria
#### Automated Verification:
- [ ] `tsc` compiles with no new errors after adding the import, fields,
  methods, and listener wiring to `InlineRunnerModal`.
- [ ] `npm run build` (type-check + esbuild) passes; `npm test` passes with no
  regressions in existing inline-runner / snippet-editor suites.
- [ ] Closing the inline runner (`close()`) detaches both `mouseup` and
  `selectionchange` listeners and nulls `createSnippetBtnEl` and
  `boundSelectionHandler` — no leaked listeners or stale DOM refs (verifiable
  by re-opening the runner and confirming no double-fire of selection events).
#### Manual Verification:
- [ ] `InlineRunnerModal` renders an always-visible create-snippet icon button
  in the footer row, to the left of (inside the same left group as) the close
  button, on every `render()` — including after `at-node`/`awaiting-loop-pick`
  re-renders that tear down and rebuild the footer.
- [ ] The create-snippet button is created with `disabled = true` on every
  render, then `updateCreateSnippetButtonState()` re-evaluates it against the
  live selection so an existing selection at render time enables it
  immediately.
- [ ] Selecting text inside `contentEl` (mouse drag then release) enables the
  create-snippet button within one `mouseup`/`selectionchange` tick; clearing
  the selection (clicking elsewhere in `contentEl`) disables it again.
- [ ] Selecting text outside `contentEl` (e.g. in the note editor behind the
  runner) does NOT enable the runner's create-snippet button —
  `getSelectedContentText()` returns `''` when the selection's anchor node is
  not contained in `contentEl`.
- [ ] Keyboard Shift+Arrow selection inside `contentEl` enables the button via
  the `document` `selectionchange` listener (covers non-mouse selection).
- [ ] Clicking the enabled create-snippet button opens `SnippetEditorModal` in
  create mode with the template textarea pre-filled verbatim with the selected
  text (verifiable via the chip editor's `templateArea.value`, the pre-fill
  path at `snippet-chip-editor.ts:125`).
- [ ] Clicking the create-snippet button when disabled does nothing (the
  browser-suppressed disabled button + the `if (template.length === 0) return`
  defensive guard both block action).
- [ ] `SnippetEditorModal` opens above the inline runner overlay (Obsidian
  modal z-index on `document.body`); the inline runner remains visible behind
  the modal. **[Risk r1 — verify explicitly.]**
- [ ] After `SnippetEditorModal` resolves (save or cancel), the inline runner
  is still open and functional; the create-snippet button reflects the
  then-current selection state.
- [ ] The runner's keyboard shortcuts (Ctrl/Alt+Left = step back,
  Ctrl/Alt+Right = redo, Escape = close) still work while the create-snippet
  button is present; the selection listener does not intercept keydown.
- [ ] The create-snippet button's aria-label uses
  `protocolRunner.createSnippetFromSelection` from the active locale (en or
  ru); the key exists in both `src/i18n/locales/en.json` and
  `src/i18n/locales/ru.json`.
