# Research: Community Library backend (Supabase + Cloudflare Pages)

## Research Question
Build the backend of the Moderated Community Library so the already-shipped plugin client actually has a registry to talk to. The developer's original intent (verbatim): *"I'd like to continue working on the Library. As I understand it, we've completed the client-side part, and now we need to build the backend to make everything work. I'd like to have a fully functional version. At the moment, I don't have a spare domain, so I'm wondering whether it's possible to implement the backend using GitHub Pages. If having a domain would make things easier, I'll arrange a new domain specifically for this project."* Stated audience: **"Just me for now"** — solo operation; success = a working, deployable version the developer controls end-to-end before opening it to contributors.

The chained discover FRD (`.rpiv/artifacts/discover/2026-08-06_08-12-45_community-library-backend.md`) fixed the shape: a new separate backend repo, Phase 1 serves the plugin's three shipped read routes as static JSON on Cloudflare Pages (`_redirects` 200-rewrites), Phase 2 layers Supabase (Auth + Postgres + Storage + Edge Functions) for the stateful submission/moderation/auth/report/revocation lifecycle + a WCAG 2.2 AA moderation dashboard SPA, with SHA-256 integrity now and ed25519 deferred, and duplicated wire types + a cross-repo parity gate. This research traces the shipped client contract the backend MUST serve, the integrity model it must reproduce, the parity-gate extension point, the registry-origin configuration, and the external hosting surfaces (Cloudflare Pages, Supabase).

## Summary
The shipped plugin client is a pure, anonymous, https-only read client with **three extension-less GET routes** and a **single configurable base URL**; its wire types and runtime guards are frozen (949/949 tests green, `DEFAULT_REGISTRY_URL=''`). The backend's overriding job is to serve this contract byte-for-byte without any client change. Concretely the backend must: emit bodies that pass `isCatalogResponse`/`isReleaseResponse`/`isPackageManifest` verbatim (`src/library/registry-model.ts:33`,`:43`, `src/library/library-model.ts:174`); serve the manifest-only route as the `{ manifest: PackageManifest }` wrapper (NOT a bare manifest, NOT the full release body); accept percent-encoded non-ASCII `packageId`/`version` path segments and echo the decoded identifiers exactly (the client downgrades identity mismatch to `unavailable`); return 404 for unknown releases (client maps 404→`not-found`) and 2xx for valid ones; and produce `protocolSha256` = SHA-256 hex of `JSON.stringify(protocolDoc, null, 2) + '\n'` plus per-snippet SHA-256 of the exact UTF-8 content bytes (lowercase hex, case-insensitive compare; NO ed25519 field).

The developer checkpoint resolved three architectural decisions: **(1) Static regen on publish** — read routes stay static JSON on Cloudflare Pages across BOTH phases; a publish/revoke webhook regenerates `catalog.json` + release/manifest `.json` reusing the phase-1 generator + `_redirects`; the custom-domain `libraryRegistryUrl` never changes; Supabase serves only the stateful write API on `*.supabase.co`. This means the Supabase Edge Function read-routes design is NOT used — reads are a static build artifact regenerated from Supabase state. **(2) Backend CI, plugin pinned** — the parity gate runs in the backend repo's CI checking out the plugin at a pinned rev; the plugin repo keeps no cross-repo gate (its `npm run check` stays green/untouched). **(3) Shared seed** — one seed definition feeds both the phase-1 static generator and the phase-2 Supabase seed migration, doubling as contract-test data.

Phase-1 Cloudflare Pages gotcha: a top-level `404.html` MUST be shipped, or Pages serves 200 (SPA fallback) for unknown release paths, which the client would classify `unavailable` instead of `not-found`. One `_redirects` splat rule (`/packages/* /packages/:splat.json 200`) covers both parameterized routes; rules match the percent-encoded path so fixture files use literal UTF-8 (decoded) names. Phase-2 Supabase gotcha: `protocolDoc` MUST be stored as TEXT (byte-exact canonical JSON), never `jsonb` (jsonb reorders keys → SHA-256 mismatch → every install fails integrity). Immutability is structural (write-once `packageId/version` Storage paths, `upsert:false`, no UPDATE/DELETE RLS policies) — Supabase has no S3 versioning. Revocation = Postgres state flip (→ read routes 404 / catalog drops the entry) + Storage object delete (Smart CDN auto-invalidates ≤60s); installed local copies keep working. Publication is atomic via a single database function (RPC) or an Edge Function holding one Postgres connection. The 9-state submission lifecycle maps to a `submissions` table + append-only `submission_events`. Auth is email magic link (PKCE); roles (author/moderator/admin) via a JWT `user_role` claim + RLS; WCAG 2.2 AA = automated axe-core (~30–57% coverage ceiling) + manual keyboard/screen-reader walkthroughs. A 2026 Supabase API-key deprecation (anon/service_role → sb_publishable_/sb_secret_) affects Edge Function JWT verification and is an open phase-2 question.

## Detailed Findings

### The frozen read contract (3 routes + wire types + transport)
The shipped client (`src/library/registry-client.ts`) composes exactly three extension-less GET URLs against a single captured `baseUrl` and validates each 2xx body with pure shape guards; it never throws (D6) and returns explicit `ok`/`not-found`/`unavailable` result states.

**Wire types (what the backend must emit):**
| Route | Body shape | Guard |
|---|---|---|
| `GET {base}/catalog` (`registry-client.ts:94`) | `CatalogResponse = { entries: CatalogEntry[]; serverTime: string }` (`registry-model.ts:10-13`) | `isCatalogResponse` (`registry-model.ts:33-41`): `entries` is an array whose every element passes `isCatalogEntry` AND `serverTime` is a string. **No schema/version sentinel on the wire** (the client stamps `radiprotocol.catalog`/`1` itself at `registry-client.ts:103-104`). |
| `GET {base}/packages/{enc(id)}/releases/{enc(ver)}` (`registry-client.ts:126`) | `ReleaseResponse = { manifest: PackageManifest; snippetContents: Array<{relPath:string; content:string}> }` (`registry-model.ts:15-18`) | `isReleaseResponse` (`registry-model.ts:43-53`): `manifest` passes `isPackageManifest` AND `snippetContents` is an array of objects with string `relPath`+`content`. |
| `GET {base}/packages/{enc(id)}/releases/{enc(ver)}/manifest` (`registry-client.ts:160`) | **wrapper** `{ manifest: PackageManifest }` — defined ONLY by the consumption site `registry-client.ts:168-169` (reads `body?.manifest`); NO exported interface | `isPackageManifest(body?.manifest)`; a bare manifest at top level → `undefined` → `unavailable`; a full `ReleaseResponse` also passes (extra keys tolerated) but the canonical body omits `snippetContents` (the route exists so the server can omit snippet bytes). |

**`PackageManifest`** (`library-model.ts:44-63`, guard `isPackageManifest` `:174-190`) — required: `schema === 'radiprotocol.package'` (`library-model.ts:10`), `version === 1` (`:12`), `packageId`/`releaseVersion` strings, `protocolDoc` passing `isProtocolDocumentV1`, `protocolSha256` string, `snippetFiles` array of `{relPath,sha256}` (each element `isPackageSnippetFile` `:155-159`), `catalogEntryId` string, `publishedAt` string; optional: `author?: {displayName:string}` (`null` rejected). **`CatalogEntry`** (`library-model.ts:66-81`, guard `isCatalogEntry` `:193-212`) — required: `packageId`, `title`, `description`, `latestVersion`, `categories:string[]` (every element a string), `updatedAt`, **`author:{displayName}` (REQUIRED, unlike the manifest)**; optional: `summary?` (`null` rejected). **`ProtocolDocumentV1`** (`protocol-document.ts:23-57`, guard `isProtocolDocumentV1` `:167-183`) — required sentinels `schema === 'radiprotocol.protocol'` (`:14`), `version === 1` (`:17`), string `id/title/createdAt/updatedAt`, `nodes`/`edges` arrays; the guard is deliberately shallow (checks `Array.isArray` only on `nodes`/`edges`, no element validation) — deep node validation happens at install via `ProtocolDocumentParser` (`library-installer.ts:236-240`), so a shape-valid-but-semantically-broken doc passes the wire guard but fails install.

**Transport behavior the backend must preserve:**
- `normalizeRegistryUrl` (`registry-client.ts:53-64`): trim → empty→`''`; invalid URL→`''`; non-`https:`→`''` when `httpsOnly` (production default `true`); strip ALL trailing slashes; **path prefixes preserved verbatim** (`https://host/api` → `https://host/api/catalog`).
- Per-segment `encodeURIComponent` on `packageId` and `version` only (`registry-client.ts:126`,`:160`); literal separators unencoded. Space→`%20` (test `registry-client.test.ts:102-108`); non-ASCII→UTF-8 percent-encoded; reserved chars→`%2F`/`%3F`/`%23`/`%25`…; a lone surrogate (`'\uD800'`) throws `URIError` inside the try → `unavailable` (never throws out).
- Status semantics (fixed order for routes 2/3): 404→`not-found` (`registry-client.ts:128-130`,`:162-164`); other non-2xx→`unavailable`; malformed body→`unavailable`; **identity check** `body.manifest.packageId === packageId && body.manifest.releaseVersion === version` (`:138-140`,`:172-174`) — mismatch→`unavailable` with reason `release identity mismatch: requested ... but manifest carries ...`. The server must decode each segment and echo the exact decoded identifier.
- `throw:false` on every request (`:94`,`:127`,`:161`); the client never sets `followRedirects` so Obsidian's default (follow) applies — only the final status/body matters; no auth, no headers, no query, no body. `CatalogFetchResult` has no `not-found` state (catalog 404→`unavailable`).

### Integrity model (SHA-256, canonical JSON — what the backend must reproduce byte-identically)
`integrity.ts:30-59`: `sha256String` = UTF-8 bytes → `subtle.digest('SHA-256')` → `toHex` (per-byte `toString(16).padStart(2,'0')` → **lowercase** 64-char hex). `verifyIntegrity` (`:56-59`): `actual.toLowerCase() === expectedSha256.toLowerCase()` — **case-insensitive** (uppercase backend hex passes, but lowercase is canonical). Never throws on mismatch.

**Exact bytes the backend must hash** (enforced at install time, NOT by any wire guard — the guards only check `typeof === 'string'`):
- `protocolSha256` = SHA-256 hex of `JSON.stringify(manifest.protocolDoc, null, 2) + '\n'` — 2-space pretty indent, single trailing `0x0A` (`library-installer.ts:233-237`; contract documented at `library-model.ts:53`). The plugin `JSON.parse`s the wire body then re-stringifies, so the backend's hash must be over a serialization whose key order + number literals match the object it ships. Store `protocolDoc` as the exact canonical text; do NOT re-serialize from `jsonb`.
- Each `snippetFiles[i].sha256` = SHA-256 hex of the UTF-8 bytes of the exact `snippetContents[i].content` string — **zero normalization** (no BOM/CRLF/trim; hashed bytes ≡ wire bytes ≡ on-disk bytes; `library-installer.ts:227-231`).

**Source-manifest hash vs. rewritten installed hash:** the manifest's `protocolSha256` verifies the SOURCE doc (`:233-237`); the installer clones the doc, rewrites snippet-node `snippetPath`/`subfolderPath` to `library/<packageId>/<version>/` (`:267-294`), then computes a DIFFERENT installed hash over `JSON.stringify(rewrittenDoc, null, 2) + '\n'` (`:329`) stored in the `InstalledRecord`. The backend only ever produces the SOURCE hash; the installed hash is a plugin concern. For packages with no snippet nodes the two coincide.

**ed25519 / authenticity confirmed absent:** `integrity.ts:5` ("ed25519 deferred"); `library-model.ts:39-42` ("NO speculative fields"); the guards contain zero signature checks. The manifest MUST carry hashes + provenance and NO signature field, or it violates the shipped client's integrity framing (D5). UI never marks unsigned releases "trusted".

### Registry-origin configuration (single base URL)
There is exactly **one** URL-bearing setting: `libraryRegistryUrl` (`settings.ts:36`, default `''` at `:46`). The effective input is `this.settings.libraryRegistryUrl || DEFAULT_REGISTRY_URL` (`main.ts:74`,`:288`) where `DEFAULT_REGISTRY_URL = ''` (`registry-client.ts:22`), so empty override + unprovisioned default both collapse to "no endpoint" (`isUnavailable()` true, `registry-client.ts:80-81`). The client is rebuilt on settings change via `rebuildLibraryServices()` (`main.ts:287-294`), which re-normalizes the URL at construction and recreates the `RegistryClient` + `LibraryService` graph (vault-file-backed store DATA survives; instances are re-instantiated). The `LibraryView` picks up the new service on its next refresh.

**The single-base-URL constraint is load-bearing:** `baseUrl` is `private readonly` (`registry-client.ts:68`), captured once at construction; there is no second URL field, no per-endpoint origin, no static/API split anywhere (grep across `src/` confirms only `settings.ts`/`main.ts`/`registry-client.ts`/i18n/tests reference it). Path prefixes ARE representable (`https://host/api` works), but two origins cannot be addressed simultaneously. This drove checkpoint decision #1: the read routes stay on ONE origin (the Cloudflare custom domain) across both phases.

### Cross-repo parity gate (extension point)
`scripts/check-consistency.mjs` is a zero-dependency Node script: `errors`/`warnings` accumulators (`:5-9`), `fail()`/`warn()`/`info()`, `readJson`/`readText`/`git`/`trackedFiles` helpers (`:11-14`), seven numbered checks, and a single failure exit at `:120` (`errors.length > 0` → `process.exit(1)`). **Check 7** (`:95-113`) is the template: `flatKeys()` (`:98-104`) flattens each i18n locale into a dotted-path `Set` (arrays/null terminate as leaf keys; nested non-null non-array objects recurse), diffs bidirectionally (`missingInRu`/`missingInEn`, `:109-110`), and calls `fail()` on either direction. The gate is strictly in-repo, in-process, text/JSON-only — no `process.env`/`process.argv` input, no cross-repo checkout (CI `.github/workflows/ci.yml:16-17` checks out only this repo; the consistency step runs at `ci.yml:31-33`), no TypeScript/schema extraction, and "missing input" = uncaught throw (hard fail). Local: `npm run check:consistency` (folded into `npm run check`, pre-push `.githooks/pre-push:11-15`).

**The extension needed (D6):** a new cross-repo Check 8 that compares the duplicated wire types (`CatalogResponse`/`ReleaseResponse`/`PackageManifest`/`CatalogEntry`/`ProtocolDocumentV1` + the `{manifest}` wrapper). A `flatKeys`-style path set is INSUFFICIENT — the wire contract carries semantics the i18n gate never needed: per-field **requiredness**, **literal sentinels** (`===` on `'radiprotocol.package'`/`1`/`'radiprotocol.protocol'`), **array element shapes**, **open maps** (`fields: Record<string,unknown>`), **literal unions** (`layoutDirection?: 'LR'|'TB'`), and **wrapper nesting**. What is needed is a canonical per-type shape descriptor (JSON-Schema-like: object → ordered list of `{name, required, kind}` where kind recursively covers object/array-of/string/number/boolean/literal/union/null/record) emitted from each repo's own definitions and compared structurally, with sentinels compared as constants. The plugin's guards are the de-facto executable contract (the FRD acceptance criteria are phrased entirely in terms of "accepted by the plugin's `isCatalogResponse`/`isReleaseResponse`/`isPackageManifest` guards"), so the plugin side of the fixture must be equivalent to what those guards accept — including recursion across module boundaries (`isReleaseResponse` → `isPackageManifest` → `isProtocolDocumentV1`).

### Phase-1 static registry on Cloudflare Pages
Cloudflare Pages `_redirects` (current docs, updated Apr 21 2026) supports `200` (true rewrite — URL stays extension-less, body comes from the destination asset), wildcards (`*` → `:splat`, greedy, includes `/`), and single-segment placeholders (`:name`); top-most rule wins; limits 2,000 static + 100 dynamic rules; relative source paths only. **Two rules suffice:**
- `/catalog /catalog.json 200`
- `/packages/* /packages/:splat.json 200` (one splat covers both `/packages/{id}/releases/{ver}` → `packages/{id}/releases/{ver}.json` and `.../manifest` → `packages/{id}/releases/{ver}/manifest.json`).

`_redirects` source patterns match the **percent-encoded** request path — rules MUST be ASCII-only (a literal space/colon breaks the parser; `:` starts a placeholder), so fixture files use **literal UTF-8 (decoded)** names (`packages/КТ-грудной-клетки/releases/1.0.0.json` serves the request `/packages/%D0%9A.../releases/1.0.0`); the JSON inside carries the decoded strings (identity check compares raw args). Keep seeded `packageId`/`version` slash-free (a `%2F` would decode into a path separator).

**Gotchas:**
- **Ship a top-level `404.html`** — without it Pages assumes SPA and serves the root document with **200** for every unmatched path; an unknown release would then return 200+HTML and the client would classify it `unavailable` (malformed) instead of `not-found`. With `404.html` present, a missing rewritten asset falls through to 404 (client maps 404→`not-found`). `_redirects` CANNOT emit a 404 status (the docs mark "Rewrites other status codes ❌").
- JSON `Content-Type` is automatic from the `.json` extension (+ `X-Content-Type-Options: nosniff`, `Access-Control-Allow-Origin: *`); no `.json` URL exposure. Default `Cache-Control: public, max-age=0, must-revalidate` + Etag/304 (ideal for catalog); optional `_headers` can set `/packages/* Cache-Control: public, max-age=86400, immutable` for immutable releases.
- HTTPS: custom domain → **Always Use HTTPS** (free plan, SSL/TLS→Edge Certificates); `*.pages.dev` redirects HTTP→HTTPS. The client is https-only anyway (`normalizeRegistryUrl` rejects `http:`), so even without a redirect the client reports `unavailable`.
- Custom domain via CNAME `registry.example.com` → `<project>.pages.dev` (no zone needed); apex requires the zone on Cloudflare. Domain-level redirects (pages.dev→custom domain) are NOT possible in `_redirects` — use Bulk Redirects.

**Seeded-fixture generation (shared seed — checkpoint decision #3):** one seed definition (packages incl. a Cyrillic id + one with a space; `protocolDoc` built like `createEmptyProtocolDocument` `protocol-document.ts:96-131`; snippets + contents) feeds a generator that computes `protocolSha256` over `JSON.stringify(protocolDoc, null, 2) + '\n'` and emits three artifacts per package from the SAME in-memory manifest (identical bytes for release + manifest routes): `catalog.json = {entries, serverTime}`, `packages/<id>/releases/<ver>.json = {manifest, snippetContents}`, `packages/<id>/releases/<ver>/manifest.json = {manifest}`; file names use decoded packageId/version. Assert mutual consistency (manifest identity === path segments === catalog entry; `snippetContents` relPath set === `snippetFiles` relPath set; `catalogEntryId === packageId`) and validate the final files with the plugin's own guards (imported or duplicated copies held honest by the parity gate). Pin `serverTime`/`publishedAt` for byte-stable deploys. The same seed feeds the phase-2 Supabase migration.

### Phase-2 stateful backend on Supabase (refined by the static-regen decision)
Checkpoint decision #1 (static regen on publish) means the **read routes stay static JSON on Cloudflare Pages across both phases**; Supabase serves the stateful WRITE API (submission, moderation, auth, report, revoke) on `*.supabase.co`, and a publish/revoke webhook regenerates the static `.json` from the Supabase state. The dashboard SPA on the Cloudflare custom domain calls the `*.supabase.co` write API; the plugin client (`libraryRegistryUrl` = custom domain) reads static JSON. The read-contract stability findings below still apply — the static JSON is generated FROM the Supabase state, so the same constraints govern what gets published.

**Read-contract stability (the static regen must preserve):** revoked releases disappear from `catalog.json` (entry rolls back to prior `latestVersion` or vanishes) and 404 on the release/manifest routes (remove the `.json` file → splat rule falls through to `404.html`); the identity check forbids re-pointing a version tag (revocation removes, never substitutes). No speculative fields on `PackageManifest`/`CatalogEntry` — revocation metadata (revoked flag + reason, FRD FR13) lives in the DB and a SEPARATE future API, never in the three frozen route bodies.

**Postgres schema sketch** (all tables RLS-enabled; `anon` gets SELECT only on published+not-revoked rows; `authenticated` gets own-submission access; `service_role` via Edge Functions bypasses RLS — never exposed):
- `profiles(id→auth.users, display_name, role check in ('author','moderator','admin'))`
- `packages(id, package_id unique slug, title, description, summary, categories text[], license default 'CC BY 4.0', author_id, latest_version, updated_at)` — RLS SELECT only when a published release exists.
- `submissions(id, package_id, release_version, submitted_by, state check in the 9 states, metadata jsonb, automated_checks jsonb, unique(package_id, release_version))` — RLS: author own rows; INSERT draft; UPDATE own in draft/changes_requested.
- `submission_events(id bigint identity, submission_id, from_state, to_state, actor_id, comment, created_at)` — append-only timestamped history (FRD FR7/FR21), written by the state-machine trigger.
- `releases(id, package_id, release_version unique, protocol_sha256 check '^[0-9a-f]{64}$', protocol_doc TEXT NOT NULL (byte-exact canonical JSON — NOT jsonb), snippet_files jsonb, object_prefix, state in ('published','revoked'), published_at, published_by, review_id, revoked_at, revocation_id)` — RLS SELECT where state='published'; NO insert/update/delete for anon/authenticated; a BEFORE UPDATE/DELETE trigger raises except for the single revoke transition inside `revoke_release()`.
- `reports(id, release_id, reported_by, reason, status, ...)`; `revocations(release_id unique, reason, revoked_by, revoked_at)`; `audit_log(actor_id, action, entity_type, entity_id, payload, created_at)` — insert-only.

**9-state lifecycle** (FRD FR7): `draft → submitted → in_review → (approved → published | rejected | changes_requested → resubmitted → in_review …)` and `withdrawn` from any author-owned pre-publication state. Enforce transitions in one `plpgsql` trigger that asserts `OLD.state → NEW.state` legality AND writes the `submission_events` row in the same transaction. `published` is terminal for the submission (the artifact moves to `releases`); a new version is a new submission + release (FRD FR10/FR22: every version re-reviewed; `unique(package_id, release_version)` blocks mutating prior versions). Automated gates (FRD FR8: schema, graph validity, dependency closure, safe paths, file types, metadata, SHA-256) run at submit (before `submitted`); results land in `submissions.automated_checks`; a failing gate cannot transition to `submitted`.

**Storage immutability** (private bucket `library/releases/<packageId>/<version>/` with `protocol.json` + `snippets/<relPath>`): Supabase has NO S3 versioning ("Deleted objects are permanently removed"), so immutability is structural — write-once version-scoped paths, `upsert:false` (overwrite denied by default → 400 `Asset Already Exists`), and NO UPDATE/DELETE/SELECT RLS policies on `storage.objects` for anon/authenticated (the Storage API itself refuses non-service mutations). The manifest is served from Postgres, not Storage (one DB read for the metadata half). `protocol_doc` is a TEXT column holding the byte-exact canonical JSON (jsonb would reorder keys and break `protocolSha256`).

**Revocation** = `revoke_release(package_id, version, reason)` (RPC, admin): one transaction inserts `revocations`, sets `releases.state='revoked'`, recomputes `packages.latest_version` to the newest remaining published release (or NULL → catalog entry vanishes), writes `audit_log` + `submission_events`, then the publish webhook regenerates static JSON (revoked release 404s; catalog drops it); the Edge Function deletes the Storage objects (Smart CDN auto-invalidates ≤60s; signed-URL expiry does NOT purge CDN, so object deletion is the authoritative cutoff). Installed local copies keep working (self-contained vault content; revocation touches nothing client-side). The `revocations`/`releases.state` rows are the auditable metadata a future revocation-warning API will read.

**Transactional publication** spans Postgres (row visibility) + Storage (bytes) — two systems that cannot share one transaction. Design: Postgres is the commit point, Storage is pre-staged. Pre-upload `protocol.json` + snippets with `upsert:false` (orphan objects from a crash are inert — no `releases` row references them; sweep by a periodic cleanup). Atomic commit via one database function `publish_release(...)` (RPC, atomic by construction) OR an Edge Function holding one pooled Postgres connection doing `BEGIN/COMMIT` (client-side multi-statement transactions are unsupported via PostgREST). Inside: `pg_advisory_xact_lock` serializes concurrent publications of the same package; upsert `packages`; insert `releases` (state 'published', byte-exact `protocol_doc`, hashes, provenance); insert `submission_events` + `audit_log`. `unique(package_id, release_version)` + the state trigger make a second publish of the same version fail the whole transaction. The release becomes visible exactly at commit (no partial-release window); a failed RPC → best-effort object delete (sweep is the backstop).

**Auth + roles + dashboard:** email magic link (Supabase Auth native) with PKCE — `signInWithOtp({email, emailRedirectTo})`, code in URL (5-min single-use), `exchangeCodeForSession`; Site URL + Redirect URL allow-list in Auth→URL Configuration; PKCE email template `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`. Hosted Supabase sends `Access-Control-Allow-Origin: *` on Auth/PostgREST (no CORS config — the dashboard SPA on the custom domain calls `*.supabase.co` out of the box); Edge Functions need explicit CORS headers. Dashboard SPA = client-only `supabase-js` PKCE (tokens in localStorage, `Authorization: Bearer` per call) — simplest for a Cloudflare Pages SPA; cookie sessions via `@supabase/ssr` need a Pages Function runtime (only if SSR/server-auth is required). Roles (author/moderator/admin) via a Custom Access Token Auth Hook injecting a `user_role` JWT claim from a `user_roles` table, enforced TWICE: RLS policies via a `security definer` `authorize(permission)` helper, AND JWT-claim checks inside Edge Functions (defense in depth — the platform `verify_jwt` only proves "valid Supabase JWT", not role). Anonymous reads have NO auth (the three read routes are static JSON; the `anon` PostgREST/RLS access is defense-in-depth for any future direct query).

**WCAG 2.2 AA dashboard** (FRD FR9): email magic links effectively satisfy **3.3.8 Accessible Authentication (Minimum)** (the W3C's own conforming example is "click a link in the e-mail"). AA-relevant new criteria: 2.4.11 Focus Not Obscured, 2.5.7 Dragging Movements (moderation queues must NOT require drag — buttons for all actions), 2.5.8 Target Size (≥24×24 CSS px), 3.3.7 Consistent Help, 3.3.8. Verification = automated (axe-core `@axe-core/playwright` in CI with `withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa','wcag22a','wcag22aa'])`, assert `violations==[]` across every screen AND state incl. error-recovery; Lighthouse/pa11y cross-check) — automated coverage ceiling ~30–57% — PLUS manual keyboard-only + screen-reader (NVDA/VoiceOver/JAWS) walkthroughs of login→queue→review→approve/reject/request-changes→publish→report-triage→revoke and error/session-expiry recovery, with `aria-live`/`role="alert"` for async moderation status/errors, focus trapping in modals, 200% zoom/320px reflow, contrast AA. Automated pass = the floor/regression backstop, NOT the conformance claim.

## Architecture Insights
- **The read contract is frozen and is the executable spec.** The plugin's guards (`isCatalogResponse`/`isReleaseResponse`/`isPackageManifest`) ARE the acceptance oracle (FRD acceptance quotes them by name). The backend converges to the plugin, never the reverse (FRD D6 "zero plugin-build restructure"; P1 "the backend MUST serve it"). Drift is caught only by the cross-repo parity gate — which must compare a structural shape descriptor (sentinels-as-constants, requiredness, array-element shapes, unions, open records, wrapper nesting), NOT `flatKeys` path sets.
- **Three distinct envelopes around one `PackageManifest`:** bare (the type), inside `ReleaseResponse.manifest` (route 2), inside the unnamed `{manifest}` wrapper (route 3, defined only at `registry-client.ts:168-169`). The manifest-only wrapper is a third wire type the backend must serve distinctly (omit `snippetContents`).
- **Integrity is behavioral, not structural.** The wire guards check only `typeof === 'string'` for hash fields; the byte semantics (2-space pretty + trailing `\n`, lowercase hex, verbatim snippet bytes) are enforced only at install time. A parity check comparing only shape would let a backend "pass" while emitting minified-JSON or base64 hashes — every install would then fail integrity. The canonical serialization dialect is the natural content of a parity fixture field. `protocolDoc` MUST be stored as byte-exact TEXT, never `jsonb`.
- **Single base URL ⇒ static read origin across phases (decision #1).** Because the client captures one `readonly baseUrl` and cannot address two origins, the read routes stay on ONE Cloudflare Pages origin across both phases; Supabase serves only the stateful write API on `*.supabase.co`; a publish/revoke webhook regenerates the static JSON. This keeps `libraryRegistryUrl` stable and the plugin untouched, and makes the read path CDN-cached/trivially fast (p95 ≤ 2s easily met).
- **Immutability is structural on Supabase.** No S3 versioning exists; rely on write-once version-scoped Storage paths + `upsert:false` + no UPDATE/DELETE RLS + a state trigger. Publication is atomic via one database function (RPC) or a single-connection Edge Function; Postgres is the commit point, Storage is pre-staged. Revocation = state flip (→ static regen drops/404s) + object delete (Smart CDN ≤60s); installed copies are self-contained and unaffected.
- **Anonymous reads + authenticated writes coexist cleanly** because the read routes are static JSON (no auth) and the stateful API is a separate Supabase surface behind magic-link auth + RLS + JWT-claim role checks. The 9-state lifecycle + audit history live in `submissions`/`submission_events` behind RLS; `anon` gets nothing on those tables. Revocation metadata is exposed via a SEPARATE future API, never on the frozen route bodies.
- **Encoding + identity is a 3-commit saga (precedent `e14c5c1`).** Raw non-ASCII broke downloads; `requestUrl` double-encoded; a `fetch()` fallback + per-segment `encodeURIComponent` was needed. The backend must accept percent-encoded segments at extension-less paths and echo decoded identity exactly — the shipped client rejects mismatch and cannot be renegotiated.
- **404.html is mandatory on Cloudflare Pages.** Without it, SPA fallback returns 200 for unknown release paths → client classifies `unavailable` not `not-found`. `_redirects` cannot emit 404.
- **Gates are load-bearing infra (precedent `f2506ec`→`4d9547c`).** Deleting/breaking the consistency gate silently broke `npm run check` for 2 days; the cross-repo parity gate must be wired into CI from day one.

- **Supabase API-key model (phase 2):** `anon`/`service_role` keys are deprecated (end of 2026) in favor of `sb_publishable_`/`sb_secret_`; Edge Functions only platform-verify JWTs via the LEGACY keys — with the new keys use `--no-verify-jwt` + `@supabase/server` auth modes (`auth: 'user'|'secret'|'publishable'|'none'`). Which key model does the backend adopt at phase-2 build time (2026-08+)? Affects Edge Function JWT verification wiring.
- **Static-regen publish webhook mechanism (phase 2):** How exactly does a Supabase publish/revoke event trigger the Cloudflare Pages rebuild that regenerates the static `.json`? Options: a Supabase Edge Function calling a Cloudflare Pages deploy hook (full rebuild); a Pages Function writing individual `.json` files into the Pages asset store; a backend job pushing the regenerated files to a git branch that Pages deploys. Affects publish latency, atomicity, and the 2s-p95 read path.
- **Future revocation-warning API shape (FRD FR13):** the backend SHALL expose revocation metadata (revoked flag + reason) via a SEPARATE API for a future client to render; surfacing revocation inside already-installed copies is a plugin-side follow-up. The exact endpoint shape is unspecified and out of scope for the three stable read routes.
- **Edge Function CPU/wall-clock limits vs. release-route fan-out:** the release route's storage fan-out (parallel snippet downloads) must fit Supabase Edge Function limits (documented 200 ms CPU / 400 s wall-clock per invocation). With the static-regen decision the read routes are static (no fan-out at read time), but the publish/revoke webhook regen must still assemble each release's bytes — verify plan-specific limits before load-testing, and consider a per-package size cap at submit.
